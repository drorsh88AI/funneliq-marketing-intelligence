### ד1 — `P11-D13` מורחב: שבעה ענפי bootstrap

סדר: `GET /api/config` → session של Supabase → **`GET /api/me` עם ה-JWT**.
⛔ אין קריאה עסקית לפני `200`. `/api/me` קיים ב-`app/auth.py:134` ומחזיר
`{email, organization, role}` — ⛔ **אין שינוי בחוזה ה-API**.

| ענף | מקור | התנהגות |
|---|---|---|
| **כשל `/api/config`** | `app/auth.py:65` (`500`, env חסר) | `שגיאה בטעינת ההגדרות. נסו לרענן את הדף.` ⛔ לפני שיש session בכלל — אין Login פעיל ואין shell |
| **אין session** | `getSession()` החזיר `null` | מסך Login. ⛔ אין קריאה ל-`/api/me` כלל — אין טוקן לשלוח, וקריאה כזו הייתה מייצרת `401` מיותר ומטעה ביומן |
| `200` מ-`/api/me` | `current_user` הצליח | מציג `authenticated-shell`, מאפשר קריאות עסקיות |
| `401` | טוקן חסר/לא תקין/פג | מנקה מצב, מעלה `session epoch`, מציג Login. ⛔ תוכן הטופס אינו נשמר |
| `403` | טוקן תקין, `organization ≠ northbound` | `forbidden-notice` · ⛔ בלי נתונים · ⛔ בלי `ניסיון חוזר` · ⛔ בלי הפניה ל-Login · `sign-out` זמין |

של Supabase אינו מוכיח `organization=northbound`, וזה בדיוק ההבדל בין `401`
ל-`403`. `SIGNED_OUT` מוריד את ה-shell ומעלה epoch ⛔ בלי קריאה.

⚠ `IA.md` §9.3 מגדיר 401 מול 403 בלבד ⇒ פער ב-IA שנסגר ב-G5, יחד עם ענף
"אין session" וענף כשל `/api/config`. מכונת מצבים של שלושה ענפים הייתה
מתרגמת תקלה רגעית ב-Supabase ליציאה מהחשבון.

### ד2 — `P11-D14` מורחב: זיהוי החלפת session, ⛔ לא שם אירוע

⚠ `supabase-js` עשוי לשגר `SIGNED_IN` גם למשתמש שכבר מחובר (מיקוד טאב,
רענון טוקן). ⇒ ⛔ אין להעלות epoch לפי שם האירוע. ההחלטה נגזרת מהנתונים.

⚠ **הבהרה מושגית — הצמד אינו "זהות session".** `user.id` + `access_token`
הם **גלאי שינוי שמרני**, ⛔ לא מזהה session: הטוקן עשוי להתחלף **בתוך אותו
session** (רענון), ולכן שינוי בו מעיד "ייתכן שמשהו התחלף" ⛔ ולא "זהו session
אחר". המנגנון בנוי סביב אי-הוודאות הזו, ⛔ לא סביב הכחשתה.

⚠ **עיקרון מנחה:** המנגנון נשען **רק על שדות top-level מתועדים** של אובייקט
ה-`Session`, ו⛔**אינו תלוי ב-JWT claim חיצוני שלא אומת מול סביבת הפרויקט**.

| רכיב | הכרעה |
|---|---|
| **הגלאי** | **`session.user.id`** + **`session.access_token`** — שני שדות top-level מתועדים, ⛔ בלי פריסת JWT |
| `user.id` | ⚠ ⛔ אינו מזהה session בפני עצמו: לאותו משתמש יכולים להתקיים כמה sessions במקביל. לכן הוא מבחין אחד מתוך שניים |
| `access_token` | ⚠ השוואת מחרוזת זהה-בייט. `SIGNED_IN` שנורה על session קיים (מיקוד טאב) נושא בדיוק אותו טוקן ⇒ ההבחנה נגזרת מהנתון עצמו, ⛔ לא מהנחה על שם האירוע |
| **עידון אופציונלי** | קיים JWT claim חיצוני מתועד שמזהה session, וניתן להשתמש בו כדי להימנע מהעלאה מיותרת. ⚠ ⛔ אינו תנאי לתקינות — ייכנס רק אחרי אימות מול סביבת הפרויקט ב-CP1. לא אומת/חסר/לא קריא ⇒ הכלל השמרני נשאר בתוקף, **והמנגנון עובד נכון בלעדיו** |

**עלות הטעות בכיוון השמרני:** ביטול בקשה אחת באוויר באירוע נדיר, והמשתמש
שולח שוב. **עלות הטעות בכיוון ההפוך:** תגובה של session ישן מרונדרת על
session חדש. ⇒ ⛔ אין סימטריה, ולכן ברירת המחדל היא שמרנית.

#### שני צירים נפרדים — ⛔ אין למזג אותם

⚠ **העלאת epoch אינה ניקוי state.**

| פעולה | מה היא עושה | טריגרים |
|---|---|---|
| **העלאת epoch** | פוסלת תשובות שבאוויר כדי שלא ירונדרו. ⛔ אינה נוגעת בקלט, בתוצאות המוצגות או בדוגמה שנטענה | כל הטבלה שלהלן — כולל הענף השמרני של `SIGNED_IN` עם טוקן שונה |
| **ניקוי state** | מוחקת קלט, תוצאות, דוגמה ואישור הקשר | `401` · `403` · מעבר אל/מ-`null` · שינוי `user.id` בלבד |

⇒ **יחס הכלה חד-כיווני:** כל ניקוי state מעלה גם epoch; ⛔ אך לא כל העלאת
epoch מנקה state. הענף השמרני (`SIGNED_IN` עם אותו `user.id` וטוקן שונה)
מעלה epoch ומבטל בקשות ישנות — ⛔ ואינו מוחק את עבודת המשתמש רק בגלל
שהטוקן התחלף.

| אירוע / תוצאה | epoch עולה? |
|---|---|
| `null` ⟷ session (בכל כיוון) | ✅ |
| `user.id` אחר | ✅ |
| `user.id` זהה אך `access_token` שונה ב-`SIGNED_IN` | ✅ — שמרני |
| `sign-out` (`SIGNED_OUT`) | ✅ |
| `401` מכל נתיב | ✅ |
| תוצאת הרשאה שמשנה מצב (`403` שמוריד shell) | ✅ |
| `SIGNED_IN` עם אותו `user.id` ואותו `access_token` | ⛔ לא — אין ביטול בקשות |
| `TOKEN_REFRESHED` עם `user.id` זהה, session לפני ואחרי | ⛔ לא |

**`TOKEN_REFRESHED` — ארבעה כללים:**

1. ⛔ אינו מעלה epoch ו⛔אינו מבטל בקשה — ⚠ אך ורק כאשר `user.id` נשאר זהה
   ויש session לפני ואחרי. שינוי `user.id` או מעבר אל/מ-`null` גוברים
   ומעלים epoch, ⛔ ללא תלות בשם האירוע.
2. ✅ מעדכן מיד את ה-JWT השמור בזיכרון — כל בקשה הבאה נושאת את הטוקן החדש.
3. ✅ מריץ `/api/me` עם הטוקן החדש לפני קריאות עסקיות חדשות. ⚠ זהו עקביות
   מצב ב-UI, ⛔ **לא** שכבת האכיפה: האכיפה האמיתית היא `Depends(current_user)`
   בצד השרת, בכל נתיב עסקי, בכל בקשה.
4. ⚠ `503`/`500` ב-`/api/me` הזה ⛔ אינו מוריד shell שכבר עובד — הוא מציג
   הודעת זמינות בלבד; קריאות עסקיות חדשות חסומות עד Retry מוצלח, אך ה-shell
   והנתונים שכבר הוצגו נשארים.

#### תלות בעובדות לא-מאומתות — עיקרון חוצה-תכנון

## י. מקרי הפרכה (יבוצעו ויתועדו, לא יוסקו)

1. טעינת דוגמה → עריכת שדה אחד ⇒ תוצאה קודמת נעלמת מיד, התווית → `תרחיש שנערך`.
2. שליחה → שינוי שדה בזמן בקשה ⇒ התשובה המאוחרת אינה מרונדרת.
3. בקשת P4S באוויר → שינוי שדה בטופס המשותף ⇒ תוצאת P4S אינה מתבטלת.
4. סימטרי ל-3: בקשת הטופס המשותף באוויר → שינוי שדה ב-P4S ⇒ אינה מתבטלת.
5. שתי שליחות רצופות באותו מסך, הישנה חוזרת אחרונה ⇒ מרונדרת רק החדשה.
6. `403` ⇒ ללא נתונים, ללא `ניסיון חוזר`, ללא הפניה ל-Login, פקד יציאה זמין.
7. `401` באמצע session ⇒ מסך התחברות; תוכן הטופס אינו נשמר.
8. `/api/me` מחזיר `503` ⇒ שגיאת זמינות + ניסיון חוזר; session נשמר, shell חסום עד Retry מוצלח.
9. כשל `/api/config` ⇒ הודעת טעינת הגדרות; אין Login פעיל ואין shell.
9א. `getSession()` מחזיר `null` ⇒ Login, ואפס בקשות ל-`/api/me`.
9ב. `SIGNED_IN` עם session תקין אך `organization ≠ northbound` ⇒ `403`; `authenticated-shell` לא הוצג לרגע.
9ג. `TOKEN_REFRESHED` בזמן בקשה באוויר ⇒ epoch אינו עולה, התשובה מרונדרת, והבקשה הבאה נושאת את הטוקן החדש.
9ד. `SIGNED_IN` חוזר בזמן בקשה באוויר — שני ענפים: (א) אותו `user.id` ואותו `access_token` ⇒ אין epoch, אין ביטול. (ב) אותו `user.id` אך `access_token` שונה, גם ללא `SIGNED_OUT` קודם ⇒ epoch עולה, בקשות ישנות נפסלות, `/api/me` מאומת לפני המשך.
9ה. `/api/me` מחזיר `500` (ב-bootstrap) ⇒ shell חסום, session נשמר, הטקסט אינו מבטיח שהמתנה תעזור.
9ו. `TOKEN_REFRESHED` → `/api/me` מחזיר `500`/`503` ⇒ shell ונתונים נשארים, epoch אינו עולה, קריאות עסקיות חדשות חסומות עד Retry=200, ואז המשך ללא אובדן state.
10. בקשה באוויר → `sign-out` ⇒ התשובה אינה מרונדרת בשום מסך.
11. בקשה באוויר → `sign-out` → התחברות מחדש ⇒ התגובה הישנה אינה מרונדרת גם ב-session החדש.

15. OOD ב-P2 בלבד ⇒ P2 ללא מספר + סיבה קונקרטית; P3/P4 מציגים מספר.
16. כשל בורר ה-prefill ⇒ הזנה ידנית ושליחה נשארות אפשריות במלואן.
17. `closed > followup_5` ⇒ שגיאה חוסמת; אין חיתוך לאפס ואין שינוי שקט ב-`closed`.

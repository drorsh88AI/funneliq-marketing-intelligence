## עובדות שנמדדו מול ה-CSV (3,500 × 19)

⚠ אלה **תוצאות בדיקה מקדימה**, לא תוצרי סקריפט. `scripts/analysis.py` עדיין
אינו קיים. בביצוע כל המדדים יופקו מחדש באופן שחזורי וייכתבו ל-`docs/`.

**התפלגויות:** `ltv_months` חסר ×4 · `cumulative_profit` חסר ×29 (33 שורות) ·
`upsell` 42% · `referred` Yes 39% · `purchased` 90% (3,163) ·
`ad_budget` 500–20,000 חציון 3,000 · `ltv_months` 1–56 ממוצע 22.

**זהויות תקינות:** `leads_answered + leads_not_answered = num_leads` ב-100% ·
מונוטוניות מלאה בשרשרת המשפך, אפס חריגות · הזהות הסוגרת היא
`closed + not_closed = followup_5` — **לא** `leads_answered` · אין ערכים
שליליים · אין `num_leads = 0` · `referred` נקי (Yes/No).

**תקציבים בדידים:** 500, 800, 1000, 1500, 2000, 2500, 3000, 4000, 5000, 6000,
7000, 8000, 10000, 12000, 15000, 20000. הפער 1501–1999 בהגדרת הטיירים של הבריף
**ריק בפועל**.

**כפילויות:** 10 שורות עודפות, **19 שורות ב-9 קבוצות**, תקציבים 500/800/1500,
כולן `purchased = 0`, **2 מהן `closed = 1`**.

**חריגות לוגיות:** 155 שורות `closed > 0` עם `purchased = 0` · 333 שורות
`purchased = 0` עם `ltv_months > 0`.

**נשירה לפי שלב:** fu1 21.7% · fu2 25.7% · fu3 18.6% · **fu4 10.4%** · fu5 29.2%.

**`calls_to_closed`** — ⚠ מתואר בבריף כממוצע ברמת רשומה, ומופיע ב-CSV בערכים
שלמים; ייתכן שעוגל או נוצר מראש כערך בדיד — אין תיעוד שמכריע. אין בו היסטוריה
פר-עסקה. חציון 3, ממוצע 3.70, מקסימום 9.
- ברמת רשומה: ב-1,519 מתוך 3,163 (48%) הערך הממוצע הוא 4 ומעלה.
- תת-אוכלוסייה `closed = 1` (n=488): **439 (89.96%) מציגות
  `calls_to_closed >= 4`.**
- התת-אוכלוסייה נבדלת תיאורית:

  | | `closed = 1` (n=488) | `closed ≥ 2` (n=2,675) |
  |---|---|---|
  | `calls_to_closed` ממוצע | 5.65 | 3.35 |
  | תקציב (חציון, רמת רשומה) | 1,000 ₪ | **4,000 ₪** |
  | לידים (חציון, רמת רשומה) | 20.5 | **47** |
  | שיעור המרה | 5.01% | 7.32% |
  | `ltv_months` ממוצע | 11.05 | 25.13 |

  מתאם `closed` ↔ `calls_to_closed` = −0.238.
  ⚠ **אין להסיק מכאן שיעור ברמת עסקה ולא את כיוון ההטיה.** יחידת ההשוואה היא
  רשומה, ורשומת `closed ≥ 2` נספרת כאחת אף שהיא מכילה כמה עסקאות. הניסוח
  "חסם עליון" הוסר — הוא לא נבע. אין לכנות את הקבוצה "קשה יותר" כעובדה.

**המרה לפי טייר:** Low 4.52% · **Mid 8.22%** · High 5.43%. לא מונוטוני.

**קולינאריות:** `leads_not_answered = num_leads − leads_answered` בדיוק.

**אחרי סינון ל-`purchased = 1` (3,163):** `purchased` הופך קבוע (`nunique = 1`)
ויורד מהפיצ'רים. ⚠ **שני מספרים שאסור לבלבל** (תפיסה של סבב 7 — היה בלבול
אצלי):
- **שיעור בסיס** `upsell = 1` = **46.35%** (1,466/3,163) — מוצג למשתמש כהשוואה.
- **majority baseline** (ניחוש `upsell = 0` תמיד) = **53.65%** (1,697/3,163) —
  מה שהמודל צריך לנצח במדדים.
- שיעור בסיס `referred = Yes` באותה אוכלוסייה = **42.71%**.

**פרופיל סופר-לקוח** (`purchased=1 AND referred=Yes AND upsell=1 AND ltv≥34`):
**529 רשומות** (16.72%) — ⚠ ספירה ברמת רשומות המקור; אין מזהה לקוח שמוכיח
ששורה = לקוח נפרד — **33.61% מסך הרווח**, CAC ממוצע **990.71 ₪** מול
**1,437.46 ₪** לכלל הלקוחות — **31.1% זול יותר**. ממצא ה-CAC יציב בכל סף
שנבדק (חציון/רבעון/עשירון).

## האפיון — מצב נוכחי

**תשתית:** FastAPI אחד + `app/static/` עם supabase-js מ-CDN · פריסה ב-**Render**
(הבריף מתיר במפורש כתחליף ל-Railway) · `git init` בתיקייה הנוכחית ·
סקריפטים `.py` בלבד, בלי notebook · README אנגלית, REPORT עברית · ממשק עברית RTL.

**ניקוי:** הכפילויות **נשמרות** (אין `id` או זמן שמוכיחים שהן שגיאות) +
`source_row_id` + ניתוח רגישות · חסר ביעד מוסר רק במשימת המידול הרלוונטית,
**לא** בספירות תיאוריות · imputation מוכרע בתוך כל pipeline · גרעיניות מעורבת
מתועדת כ**השערת עבודה** בארבע שכבות (ידוע / נצפה / מוסק / השפעה).

**Snapshot:** P2/P3/P4 — **בתום מחזור הקמפיין שבו הלקוח נרכש**. P6 — ברגע
הקצאת התקציב. גרסה מוקדמת אחרי follow-up 1 היא **ניסוי מחקרי בלבד**, לא
production.

**אוכלוסיות:** P2/P3/P4 על `purchased = 1` (3,163). מודל P4 על כלל 3,500 הוא
ניתוח רגישות ב-REPORT בלבד — CV לא יכול להכריע בין אוכלוסיות עם דנומינטורים
ושיעורי בסיס שונים.

**מתודולוגיה:** 5-fold CV עם **ממוצע ± סטיית תקן** · stratified רק ב-P3/P4,
ו-P2/P6 פיצול רגרסיה עם seed קבוע · **השוואת משקולות** ב-P3 במקום הכרעה מראש ·
CV מקונן ל-tuning ב-P4 · **Brier + עקומת כיול** לציון 0–100 · כל preprocessing
בתוך `Pipeline`/fold · פרופילי תקציב ב-P6 מחושבים **בתוך כל fold מנתוני אימון
בלבד** · Holdout סגור עד אחרי בחירת המודל, מדדיו מדווחים פעם אחת.

**מדיניות ארטיפקט — נקבעה מראש, לא משתנה לפי תוצאת ה-Holdout:** נפרס ארטיפקט
ה-**Evaluation** שאומן על train בלבד. Refit על train+holdout הוא הרחבה עתידית.
כל ארטיפקט = Pipeline מלא + metadata (סדר עמודות, טיפוסים, target, snapshot,
אוכלוסייה, `evaluation`/`production`, גרסה, מדדים, checksum).

**סימולטור P6:** ₪50,000 ב-**2×20,000 + 10,000** · 10×5,000 · 25×2,000 ·
100×500 — כל אסטרטגיה נבדקת שהיא מסתכמת בדיוק ב-50,000. פרופיל חציוני לכל
תקציב מדויק. n לכל תקציב מדווח, טווח אי-ודאות מורחב במדגם קטן. אין
extrapolation מחוץ ל-500–20,000, אין טענה סיבתית.

**הסבר:** feature importance לשלושת המודלים + **SHAP למודל הזוכה, offline
בלבד**. אפס תלויות חדשות — שלושת ה-boosters מחשבים SHAP נייטיבית.

**Auth:** הרשמה ציבורית **כבויה**, משתמשים נוצרים ידנית · הרשאה ב-`app_metadata`
(`organization=northbound`), לעולם לא `user_metadata` · RLS:
`using (auth.jwt() -> 'app_metadata' ->> 'organization' = 'northbound')` ·
משתמש דמו מאומת מראש למנחה, איפוס סיסמה ע"י מנהל · `/health` ו-`/api/config`
**ציבוריים**, כל השאר דורש JWT + הרשאה (401 / 403).

**חמש שאלות המייסד:** `/api/predict/ltv` (P2) · `/api/predict/upsell` (P3) ·
`/api/predict/referral` (P4) · `/api/simulate/budget` (P6) ·
`/api/insights/followup` (P5). טופס משותף ל-P2/P3/P4 עם **prefill חובה**.
⚠ ציון P4 הוא **נטייה להפניה**, proxy מוקדם ללקוח-על — לא הסתברות לעמוד
בשלושת התנאים.

**מסקנת P5 — תיאורית, לא סיבתית.** הנתונים אינם תומכים בעצירה אוטומטית אחרי
המעקב השלישי; הם גם אינם מוכיחים שמנהל המכירות טועה. ההמלצה: ניסוי תפעולי
מבוקר למדידת סגירה שולית, זמן ועלות.

**ה-CSV מחוץ ל-repo — מקומי ו-ignored.** *(היפוך מההחלטה המקורית — ראו יומן
ההכרעות למעלה, "ה-CSV ב-repo הציבורי → בוטל".)*

**עיצוב:** פרויקט Stitch **חדש** ל-FunnelIQ. החיבור נבדק ועובד (קריאה בלבד).
שלושת הפרויקטים הקיימים שייכים לעבודה אחרת ולא ייגעו. הצעה למחזר מערכת עיצוב
מפרויקט ביטוח **נשקלה ונדחתה**: מה שהיה עובר הוא ארבע מוסכמות שנכונות לכל
אפליקציה בעברית; מה שייחודי בה שייך לדומיין הביטוח.

**הצגת אי-ודאות:** טווח שמוצג **חייב שיטת חישוב מתועדת** — אין פס שרירותי לפי
גודל מדגם. P2: **Split Conformal** (`תחזית: 24 חודשים` + `טווח: 18–31`);
אין להציג RMSE/std של CV כטווח אישי. P3: הסתברות + השוואה לשיעור בסיס 46.35% +
קטגוריית נטייה. P4: כותרת **"נטייה להפניה"** (לא "ציון לקוח-על") + 0–100 +
שיעור בסיס 42.71% + הסתייגות גלויה + סטטוס כיול + גרסת מודל. P6: **Bootstrap**
+ `n` + רמת ראיות; חפיפת טווחים ⇒ אין מנצחת ודאית. מדדי מודל שייכים ל"פרטי
מודל", לא לצד כל חיזוי.

**פיצול לשלושה:** train / **calibration** / holdout. לסט ה-calibration שני
תפקידים: Split Conformal ל-P2, **והתאמת המכייל** ל-P3/P4.

**כיול — מדידה אינה כיול, והשיטה נעולה מראש.** Brier ועקומת כיול **מודדים**
ואינם מכיילים. השיטה היא **`sigmoid`, נקבעה לפני פתיחת סט ה-calibration**.
*(בחירה בין sigmoid ל-isotonic על אותו סט שמתאים אותם היא הערכה אופטימית —
הסט לא יכול גם להתאים וגם לשפוט. `isotonic` אינו חלק מה-production.)*
מודל והיפר-פרמטרים ב-CV על train בלבד → calibrator מותאם פעם אחת על
ה-calibration → **Holdout פעם אחת להערכת המערכת המלאה** (preprocessing + model
+ calibrator). חל על **P3 וגם P4**. `calibration_status = calibrated` רק אם
ההתאמה הצליחה; אחרת `uncalibrated` + אזהרה. שדות: `calibration_status`,
`calibration_method`.

**SQL — חלוקת אחריות.** SQL לאחסון, שליפה, הרשאות ואגרגציות יציבות; Python
לניקוי אנליטי, סטטיסטיקה ו-ML. `schema.sql` (טיפוסים, PK, `source_row_id`,
policies של RLS) · שאילתות Runtime מתועדות ל-`insights/followup` ו-
`insights/budget-tiers` · בדיקות Data-Contract ש**מדווחות** חריגות ולא מוחקות ·
בדיקות RLS בשלושה מצבי משתמש · **מקור אמת יחיד לטיירי התקציב** + בדיקת parity
אם ההגדרה חיה גם ב-view וגם ב-Python.
**בחוץ:** אינדקסים (3,500 שורות — קישוט; להוסיף רק אם `EXPLAIN` יראה צורך) ·
`CHECK` מעבר ל-`NOT NULL` מדוד (יסתור את מדיניות שמירת החריגות) · stored
procedures · ETL. `views.sql` רק אם ייבחרו views בפועל.

**Bootstrap ל-P6 — על רשומות, לא על folds.** בכל חזרה דוגמים רשומות מנתוני
האימון עם החזרה, ומריצים מחדש את **כל** הצינור (preprocessing, התאמת מודל,
פרופילי משפך לכל תקציב, סימולציית ארבע האסטרטגיות). אחוזונים 2.5/97.5 שנקבעים
מראש ⇒ `interval_method = bootstrap_percentile`. מספר החזרות נקבע ומתועד מראש,
לא נבחר אחרי הסתכלות על התוצאה. ה-Holdout אינו נכנס לדגימות. הטווח אינו מבטל
את מגבלת הסיבתיות ואת הנחת האדיטיביות.

**שפת הגרפים:** טכני באנגלית (כותרות, צירים, מקרא, שמות feature), הסבר
ומסקנות בעברית. הנימוק הוא **עקביות מול ה-CSV, הקוד ו-SHAP** — לא matplotlib
ולא שפת ה-README (שנשאר עברית). חל על ארבע התצוגות. מיפוי במופע ראשון
(`cumulative_profit — רווח מצטבר`) בלי לשנות את שם המשתנה בגרף. אין להוסיף
תלות bidi.

**מתי לא מציגים מספר:** קלט לא תקין ⇒ validation error · **OOD** ⇒
`אין מספיק נתונים לחיזוי אמין` + סיבה · מדגם קטן ⇒ רמת ראיות נמוכה + טווח רחב,
ואם אין טווח תקף — אין המלצה חד-משמעית.

**Tokens חדשים:** `evidence-high/medium/low` · `prediction-range` ·
`model-disclaimer` · `out-of-distribution` · `calibrated`/`uncalibrated`.
אין הסתמכות על צבע בלבד — טקסט + אייקון. צבעי אי-ודאות ניטרליים/ענבריים.

**חוזי תגובה:** `point_estimate` · `lower_bound` · `upper_bound` ·
`interval_method` · `event_probability` · `base_rate` · `propensity_band` ·
`evidence_level` · `sample_size` · `in_training_domain` · `warnings` ·
`model_version` · `calibration_status`.

**Dataviz:** נשירה ודירוג אסטרטגיות — **SVG ידני ונגיש** בדפדפן. כיול ו-SHAP —
matplotlib → **SVG**. עד 5 צבעים סמנטיים · מספרים וצירים LTR בתוך RTL ·
עמודות מאפס · fallback טבלאי לגרפים חיים · בלי 3D/עוגה/ציר כפול/גרדיאנטים.

2. **תוויות הגרפים ה-offline באנגלית.** ייצוא ל-SVG נכון, אבל **matplotlib
   אינו מטפל היטב ב-bidi עברי**. עקומת הכיול וגרף SHAP נועדו ל-REPORT ולמנחה,
   וה-README אנגלית ממילא. רק הגרפים החיים בדפדפן נושאים תוויות עבריות.

**נגזרת מבנית:** conformal דורש סט calibration שאינו ה-Holdout ⇒ הפיצול הוא
**train / calibration / holdout**, seed קבוע, stratified ב-P3/P4.

# [שולב] נספח ביקורת שמיני — Bootstrap, כיול ושפת הגרפים

יש לשלב את שלוש ההכרעות הבאות ישירות בגוף `eager-popping-spark.md`. אין לבצע
קוד, עיצוב בפועל, קריאת Stitch כותבת, פריסה או commit.

## 1. P6 — Bootstrap על רשומות, לא על folds

יש להסיר את הניסוח `Bootstrap על folds האימון`. חמישה folds אינם יחידות דגימה
מתאימות ל-Bootstrap ואינם מספקים התפלגות אי-ודאות תקפה.

הפרוטוקול המתוכנן:

1. בכל חזרת Bootstrap דוגמים מחדש **רשומות מתוך נתוני האימון**, עם החזרה.
2. בתוך כל דגימה מריצים מחדש את כל צינור P6 הרלוונטי: preprocessing, התאמת
   המודל, חישוב פרופילי המשפך לכל תקציב וסימולציית ארבע האסטרטגיות.
3. לכל אסטרטגיה שומרים את הרווח הכולל החזוי בכל חזרה.
4. הטווח נגזר מאחוזונים מוגדרים מראש של התפלגות ה-Bootstrap, למשל 2.5% ו-97.5%
   לטווח 95%, ומדווח כ-`interval_method = bootstrap_percentile`.
5. מספר החזרות ייקבע מראש לפי זמן הריצה ויציבות האחוזונים, יתועד ב-metadata
   וב-REPORT, ולא ייבחר לאחר הסתכלות על התוצאה הרצויה.

ה-Holdout אינו נכנס לדגימות. הטווח משקף שונות מדגמית ומודלית תחת ההנחות של
הסימולטור; הוא אינו מבטל את מגבלת הסיבתיות או את הנחת האדיטיביות.

## 2. P3/P4 — מדידה אינה כיול

Brier score ועקומת כיול מודדים את איכות הכיול, אך אינם מכיילים את המודל.
אם הממשק מציג הסתברות כ-`calibrated`, יש להגדיר תהליך כיול מפורש למודל הזוכה
בלבד:

- סט ה-calibration נשמר נפרד מנתוני התאמת המודל ומה-Holdout.
- לאחר בחירת המודל וה-hyperparameters על train/CV, מתאימים calibrator על סט
  ה-calibration בלבד.
- יש להשוות `sigmoid` מול `isotonic` בפרוטוקול שנקבע מראש. בשל גודל המדגם,
  sigmoid הוא ברירת מחדל יציבה יותר; isotonic ייבחר רק אם יש די דוגמאות בכל
  מחלקה והוא משפר Brier/עקומת כיול על בסיס הערכה שאינה כוללת את ה-Holdout.
- ה-Holdout משמש פעם אחת להערכת המערכת המכוילת הסופית.
- ה-metadata וה-API יחזירו `calibration_status`, `calibration_method` וגרסת
  המודל/המכייל.
- אם לא בוצע כיול מפורש או שהכיול נכשל, אין להציג `calibrated`; הממשק יציג
  `uncalibrated` והסתייגות מתאימה.

יש להחיל זאת על P3 וגם על P4. אין לטעון שעצם קיומם של Brier score ועקומת כיול
הופך את ההסתברויות למכוילות.

## 1. `90%` אינו חסם עליון על כלל העסקאות

הניתוח הנוסף של תת-האוכלוסייה `closed = 1` מעניין וניתן להשאיר את המדדים
התיאוריים שלו, אך הוא אינו מוכיח שהשיעור 89.96% הוא חסם עליון מתמטי על שיעור
העסקאות הכולל:

- יחידת ההשוואה היא רשומה/קמפיין משוער, לא עסקה בודדת.
- `calls_to_closed` הוא ממוצע ברמת רשומה.
- רשומת `closed >= 2` מקבלת משקל של רשומה אחת אף שהיא מכילה כמה עסקאות.
- לכן השוואת ממוצעים והתפלגויות בין קבוצות הרשומות אינה מספקת חסם על שיעור
  העסקאות הבודדות.

יש להסיר בכל מקום את המונח **"חסם עליון"** ואת הטענה שהחלת 90% על כלל העסקאות
בהכרח תפריז. הניסוח התקין:

> בתת-האוכלוסייה `closed = 1`, 439 מתוך 488 רשומות מציגות
> `calls_to_closed >= 4`. הקבוצה נבדלת תיאורית בגודל, בתקציב, בהמרה ובמספר
> השיחות, ולכן אינה מייצגת בהכרח את כלל הרשומות או העסקאות. לא ניתן להסיק ממנה
> את שיעור העסקאות הכולל או את כיוון ההטיה.

אין לכנות את הקבוצה "קשה יותר" כעובדה. ניתן לומר רק שנמדדו בה תקציב ולידים
נמוכים יותר, המרה נמוכה יותר ו-`calls_to_closed` גבוה יותר.

## 2. מספר שלם אינו מוכיח עיגול

יש להסיר את הקביעה ש-`calls_to_closed` "מאוחסן כמספר שלם, כלומר מעוגל". עצם
העובדה שהערכים שלמים אינה מוכיחה כיצד נוצרו. הניסוח התקין:

> `calls_to_closed` מתואר בבריף כממוצע ברמת רשומה ומופיע ב-CSV בערכים שלמים.
> ייתכן שעוגל או נוצר מראש כערך בדיד; אין תיעוד שמכריע כיצד חושב.

# [שולב חלקית] נספח ביקורת תשיעי — נעילת כיול, SQL ותיקון שפה

למרות ההכרזה "אפס החלטות פתוחות", שלושת הסעיפים הבאים טרם שולבו במצב הנוכחי.

## 1. P3/P4 — שיטת הכיול נקבעת מראש

יש להסיר את ההצעה להתאים גם `sigmoid` וגם `isotonic` על אותו calibration set
ולבחור ביניהם לפי ביצועיהם עליו. שימוש באותו סט להתאמת המכייל ולהערכת הבחירה
בין שיטות נותן הערכה אופטימית.

ההכרעה המחייבת לפרויקט:

- שיטת הכיול ל-P3 ול-P4 תהיה **`sigmoid`**, נקבעת מראש לפני פתיחת סט
  ה-calibration.
- המודל וה-hyperparameters נבחרים באמצעות CV על train בלבד.
- לאחר הנעילה, calibrator מסוג sigmoid מותאם פעם אחת על סט ה-calibration.
- ה-Holdout משמש פעם אחת בלבד להערכת המערכת המלאה — preprocessing, model
  ו-calibrator.
- Brier score, עקומת כיול ויתר המדדים מדווחים על Holdout עבור המערכת הסופית.
- `isotonic` אינו חלק מגרסת ה-Production של הפרויקט. ניתן להזכירו כאפשרות
  עתידית עם יותר נתונים או nested calibration protocol, אך לא לבצע בחירה בינו
  לבין sigmoid על אותו calibration set.
- ה-API וה-metadata יחזירו `calibration_status=calibrated` רק אם התאמת sigmoid
  הצליחה; אחרת `uncalibrated` עם אזהרה.

## 2. SQL — שימוש מפורש ומוגבל היטב

יש להוסיף לאפיון סעיף SQL מפורש. SQL אינו תוספת קישוטית אלא חלק אמיתי משכבת
Supabase/Postgres. החלוקה המחייבת: **SQL לאחסון, שליפה, הרשאות ואגרגציות יציבות;
Python לניקוי אנליטי, סטטיסטיקה ו-ML.**

### תוצרי SQL מתוכננים

- `schema.sql` — יצירת `funnel_records`, טיפוסי עמודות, primary key ו-
  `source_row_id` כמפתח יציב לטעינה חוזרת.
- אילוצי `CHECK` רק עבור כללים שהבריף והנתונים מוכיחים ושמתאימים לשמירת המקור;
  אין להוסיף constraint שעלול למחוק או לדחות חריגות שאמורות להישמר לניתוח.
- אינדקסים רק לפי שאילתות Runtime אמיתיות, למשל שדות סינון/קיבוץ כמו
  `ad_budget` או `purchased`; יש לאמת באמצעות `EXPLAIN` ולא ליצור אינדקס לכל
  עמודה באופן אוטומטי.
- RLS ו-policies ב-SQL לפי
  `auth.jwt() -> 'app_metadata' ->> 'organization' = 'northbound'`.
- `views.sql` או views בתוך `schema.sql` עבור אגרגציות Runtime יציבות בלבד,
  כגון תצוגת budget tiers ותצוגת follow-up summary, אם הן מפשטות את הדשבורד
  ומונעות שכפול לוגיקה.
- שאילתות SQL מתועדות עבור לפחות פיצ'ר Runtime אחד שהאפליקציה צורכת בפועל
  מ-Supabase, בהתאם לדרישת הבריף.
- בדיקות SQL/Data Contract: ספירת שורות, חסרים, כפילויות וזהויות המשפך —
  כבדיקות שמדווחות חריגות, לא כפעולות שמוחקות נתונים.
- בדיקות RLS: anon חסום, authenticated ללא organization חסום, משתמש Northbound
  מורשה לקריאה.

### מקור אמת ומניעת כפילות

- לוגיקת budget tiers תוגדר פעם אחת באופן קנוני. אם היא ממומשת ב-view לצורכי
  Runtime וב-Python לצורכי אימון, יש בדיקת parity שמוודאת אותן הגדרות גבול.
- אין להעביר ל-SQL אימון מודלים, CV, SHAP, conformal, bootstrap או כיול.
- אין ליצור stored procedures או שכבת ETL מורכבת ללא צורך עסקי מוכח.
- יש להוסיף לעץ הקבצים `views.sql` רק אם אכן נבחרו views; אחרת לרכז הכול
  ב-`schema.sql` ולתעד את ההחלטה.

יש לעדכן את פאזה 3 (`feat/supabase-data`) כך שתכלול schema, constraints,
indexes, RLS, queries/views ובדיקות SQL, ולהוסיף את הראיות המתאימות ל-REPORT.
